# PULSO NEXUS — E0-R2: Arquitectura revisada (respuesta a la revisión E0-R1)

## Contexto

E0 recibió el dictamen **REVISE** en la revisión independiente E0-R1. Se mantiene el enfoque: monolito modular, motores puros, snapshots inmutables, contratos versionados y una ejecución unificada manual y programada. Este documento corrige los hallazgos R1 a R7 y sustituye a E0 donde haya contradicción. Sigue en modo de planificación: no hay código, no se toca el repositorio ni la infraestructura y no se avanza a E1 sin aprobación expresa.

Convención:
- **[H]** Hecho proporcionado por el usuario o el revisor, o observado en el repositorio.
- **[D]** Decisión propuesta.
- **[X]** Decisión descartada.
- **[?]** Desconocido o pendiente.

No he validado ningún servidor, instancia, fuente ni sistema corporativo.

## 2. R1 — Persistencia y concurrencia en SQL Server

### 2.1 Supuestos de base
- **[H]** El objetivo es SQL Server. El laboratorio es independiente de la base productiva pero comparte instancia con ella.
- **[?]** Versión y edición, collation, si `ALLOW_SNAPSHOT_ISOLATION` o `READ_COMMITTED_SNAPSHOT` están activos, la política de despliegue de DDL por parte de los DBA, y la autenticación (SQL o Windows/AD).
- **[D]** El diseño solo usa funcionalidades disponibles desde SQL Server 2016 SP1: índices filtrados, `datetime2`, `OUTPUT`, `SEQUENCE`, tablas temporales y permisos por columna. Las funcionalidades de 2022, como las tablas ledger, quedan como opción si la versión lo permite.

### 2.2 Acceso y despliegue
- **[D]** Se usa `pyodbc` con Microsoft ODBC Driver 18 y **T-SQL explícito**, sin ORM. Las garantías dependen de pistas de bloqueo que conviene ver literalmente en el código.
- **[D]** Las migraciones son scripts `.sql` numerados e idempotentes, con una tabla `nexus.schema_version`. Las aplica personal autorizado (DBA). **Los logins de ejecución no tienen permisos de DDL.**
- **[H/D]** **Destino**: un esquema propio `nexus` dentro de la base de laboratorio existente **`PULSO_MAGNUM_STAGE`**, que está en una instancia compartida con producción. El uso de ese esquema está sujeto a autorización. **No se propone crear otra base corporativa ni otra instancia.** No se crean objetos en bases productivas.
- **[H/D]** **Desarrollo offline**: una instancia SQL Server **temporal y local**, con datos sintéticos y sin ninguna conexión corporativa. Se destruye al terminar.

### 2.3 Protección por instancia compartida
- **[D]** **Guard de entorno** al conectar: se comprueban `@@SERVERNAME`, `DB_NAME()` (`PULSO_MAGNUM_STAGE` en el laboratorio, o el nombre de la instancia temporal offline) y una fila sentinel `nexus.environment(name)`, y deben coincidir con la configuración esperada. Todo el acceso queda limitado al esquema `nexus`. Si no coinciden, el proceso aborta antes de cualquier escritura. Las operaciones de limpieza de pruebas exigen `environment = 'LAB'`.
- **[D]** Se fija `SET LOCK_TIMEOUT` acotado, las transacciones son cortas (solo metadatos, nunca datos voluminosos) y no se usa `NOLOCK`. No se conceden `KILL`, `ALTER ANY CONNECTION` ni roles de servidor. Las pruebas de carga en el laboratorio son acotadas y se acuerdan con los DBA.
- **[D]** Los datos tabulares voluminosos van a archivos (§4), no a SQL. Así la carga sobre la instancia es mínima.

### 2.4 Modelo de tablas (conceptual)
- `run_request`: `idempotency_key UNIQUE`, `trigger` (manual o scheduled), solicitante y parámetros.
- `scope_lease`: una fila por ámbito con `holder`, `fencing_token BIGINT`, `expires_at datetime2` y `state`.
- `run`, `run_event` (append-only), `snapshot`, `artifact`, `generation` y `generation_artifact`.
- `finding`, `policy` (versión, hash, autor, aprobador, estado), `certification`, `publication_pointer` (canal, `generation_id`, `version BIGINT`) y `publication_history` (append-only, con `prev_hash`).
- Inmutabilidad: los principales de ejecución tienen `INSERT` sin `UPDATE`/`DELETE` sobre tablas append-only. Los cambios de estado solo se hacen mediante procedimientos.

### 2.5 Primitivas transaccionales
- **Reloj**: todas las expiraciones usan `SYSUTCDATETIME()` del servidor. Nunca el reloj del worker.
- **Reclamar una solicitud**: patrón de cola con `UPDATE TOP(1) … WITH (UPDLOCK, READPAST, ROWLOCK) … OUTPUT inserted.*` dentro de un CTE ordenado.
- **Lease más fencing** (`usp_acquire_lease`): se incrementa `fencing_token` y se fija `expires_at` con `UPDATE scope_lease … WHERE scope=@s AND (holder IS NULL OR expires_at < SYSUTCDATETIME())`, y se devuelve el token con `OUTPUT`. Exactamente una fila o ninguna.
- **Heartbeat y escrituras con fencing**: todo procedimiento de estado recibe `@fencing_token` y verifica `scope_lease.fencing_token = @token AND expires_at > SYSUTCDATETIME()` leyendo la fila con `UPDLOCK, HOLDLOCK` en la misma transacción. Si la condición falla, se lanza un error y no se escribe nada.
- **[X]** `sp_getapplock` como mecanismo principal: depende de la sesión, no ofrece fencing y se pierde silenciosamente si cae la conexión.
- **Un run activo por ámbito**: lo garantizan el lease y un índice único filtrado sobre `run(scope) WHERE is_terminal = 0` como red de seguridad.
- **Publicación CAS** (`usp_publish`, §6): `UPDATE publication_pointer SET generation_id=@g, version=version+1 WHERE channel=@c AND version=@expected`. Se exige `@@ROWCOUNT = 1` y el `INSERT` en `publication_history` va en la misma transacción.
- **Deadlocks (1205) y timeouts**: los procedimientos son idempotentes (claves naturales e idempotency keys) y el cliente reintenta con backoff acotado.

### 2.5.1 Precisiones de concurrencia (revisión final; se demuestran en E1-B/E1-C con pruebas adversariales)
- **`READPAST` bajo RCSI**:
  - Con RCSI activo, un `SELECT` en `READ COMMITTED` lee versiones y no toma bloqueos compartidos. Por eso **un `SELECT … READPAST` no sirve como cola** y nunca se usa para reclamar trabajo.
  - Toda reclamación es una **sentencia de modificación** (`UPDATE … OUTPUT`) con `UPDLOCK, READPAST, ROWLOCK`. Las modificaciones toman bloqueos U/X independientemente de RCSI.
  - Cada procedimiento fija `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` al inicio para no heredar `SNAPSHOT` de la sesión, nivel en el que `READPAST` exige combinarse con pistas de bloqueo.
  - Las lecturas de control (validar lease y token, estado previo a publicar) usan `UPDLOCK, HOLDLOCK`, o `READCOMMITTEDLOCK` cuando solo leen, para que nunca decidan sobre una versión obsoleta.
  - La matriz de pruebas de E1-B se ejecuta con RCSI **ON y OFF** y con la sesión en `SNAPSHOT`.
  - **[?]** El estado real de RCSI en `PULSO_MAGNUM_STAGE` (P12) y el impacto en tempdb (version store) de una instancia compartida.
- **Workers muertos**:
  - El lease expira según `SYSUTCDATETIME()` del servidor.
  - `usp_recover_expired` puede invocarlo cualquier worker al reclamar trabajo, o el comando `nexus recover`. Toma el lease vencido **incrementando `fencing_token`**, marca el run como `FAILED(LEASE_EXPIRED)` y la generación `OPEN` como `ABANDONED` (nunca publicable).
  - Después re-encola la solicitud como un nuevo *attempt*, con su propio `run_id` y `gen_id`, hasta un máximo configurable de intentos.
  - Los archivos del intento muerto quedan en su directorio propio y los elimina el recolector (§4.2).
- **Lease caducado con el worker vivo** (pausa o partición de red):
  - Si el heartbeat falla, el worker debe detenerse de inmediato.
  - Cualquier escritura SQL posterior se rechaza por el token.
  - Lo que escriba en el FS cae en el directorio de *su* `gen_id`, ya abandonado. Ninguna generación nueva comparte ruta con él, así que no puede contaminarla.
- **Fencing de todas las escrituras**:
  - **SQL**: todo procedimiento que escribe estado recibe `(@run_id, @fencing_token)` y lo verifica en la misma transacción contra `scope_lease` con `UPDLOCK, HOLDLOCK`, lo que lo serializa frente a una toma de lease concurrente. Las únicas escrituras sin token son las de `run_request` (idempotentes) y las de los roles de validación, certificación y publicación, que no operan con el lease del productor y tienen sus propios controles (§6).
  - **FS**: el almacenamiento no admite fencing nativo. El fencing es **indirecto**: rutas exclusivas por `gen_id`, registro SQL con token obligatorio, y una certificación que no confía en archivos del productor (§4.5).
- **Transacciones interrumpidas**:
  - Todos los procedimientos usan `SET XACT_ABORT ON`. Cualquier error o *attention* (timeout del cliente) revierte la transacción completa y libera los bloqueos.
  - Ante un error o timeout, el cliente **descarta la conexión**: no la devuelve al pool en estado dudoso.
  - **Commit ambiguo** (se pierde la conexión durante el `COMMIT`): el cliente no reintenta a ciegas. Primero consulta el estado por clave de idempotencia u operación y solo reintenta si la operación no consta.
  - Una caída del proceso a mitad de transacción provoca rollback en el servidor al cerrarse la sesión.

### 2.6 Lectura de datos manuales (captura)
- **[D]** El orden de preferencia, que queda registrado en el manifiesto del snapshot como `consistency_level`, es:
  1. `SNAPSHOT` isolation, si la base lo permite: consistencia entre tablas.
  2. Una sentencia por tabla en `READ COMMITTED`: consistencia por tabla. El snapshot se marca así y la certificación decide si esto es aceptable.
- **[D]** La reproducibilidad nunca depende de volver a consultar SQL, sino de los bytes capturados (§4 y §5).
- **[D]** El orden canónico se aplica en Python con comparación binaria explícita, sin depender de la collation de la DB.

## 4. R3 — Coherencia entre generaciones SQL y artefactos

### 4.1 Invariantes
- **I1**: toda fila `artifact` en estado `VERIFIED` corresponde a un archivo que existió, era durable y tenía el hash registrado en el momento de la verificación.
- **I2**: SQL nunca referencia un archivo antes de que sea durable y esté verificado.
- **I3**: no se elimina un archivo mientras exista una referencia viva. La retirada se decide en SQL antes de tocar el FS.
- **I4**: una generación solo es publicable si toda su lista de artefactos ha sido reverificada después de sellarla, tanto por el certificador como por el publicador.
- **I5**: ante una corrupción o una ausencia detectada, el sistema falla cerrado: no publica y no sirve datos.

### 4.2 Protocolo de escritura y publicación
1. **Escritura en staging**: `staging/<run_id>/<uuid>.tmp` en el **mismo volumen** que el destino. Se calcula el `content_hash` mientras se escribe.
2. **Durabilidad**: `fsync(archivo)`, luego `rename` atómico a `generations/<gen_id>/<content_hash>.parquet` y `fsync(directorio)`. Si el destino existe con otro hash, se aborta y se pone en cuarentena.
3. **Verificación de relectura**: se relee desde la ruta final y se recalcula el hash.
4. **Registro**: `usp_register_artifact` (con fencing) inserta la fila `VERIFIED` con hash, tamaño y ruta relativa.
5. **Sellado**: `usp_seal_generation` calcula el `manifest_hash`, que es el hash de la lista ordenada de (contrato, `content_hash`, `logical_hash`), junto con la huella de entorno y los ids de snapshots. A partir de ahí la generación queda `SEALED` e inmutable.
6. **Validación y certificación con promoción**: el certificador **no confía en los hashes declarados por el productor**. Lee los bytes del área de trabajo, recalcula `content_hash` y `logical_hash`, y **copia** cada artefacto al área `certified/<gen_id>/`, en la que el productor no tiene permiso de escritura. Después lo relee y lo verifica. Cualquier discrepancia con lo declarado se rechaza. La `certification` registra los hashes **calculados por el certificador** y se vincula a `manifest_hash` y `policy_hash` (§4.5 y §6).
7. **Verificación previa a publicar**: el publicador vuelve a verificar existencia y hash y registra `verification(gen_id, at)`.
8. **Publicación**: `usp_publish` exige, en una transacción, una certificación válida, una verificación de menos de *T* minutos y el CAS (§2.5).

**Recuperación por caída en cada paso:**
- Pasos 1–3: queda un archivo huérfano sin fila. El recolector lo elimina después de un periodo de gracia, solo si no hay fila y el run está terminado.
- Pasos 4–5: la generación queda `OPEN` y el run pasa a `FAILED` al expirar el lease. Nunca será publicable.
- Pasos 6–8: no hay cambio de puntero. El estado anterior sigue vigente.

### 4.3 Retención y eliminación
- **[D]** Las rutas tienen propietario (por generación o por snapshot), sin deduplicación global [X]. Esto evita referencias cruzadas entre generaciones.
- Estados del snapshot: `AVAILABLE → RETIRING → DELETED`. Un run solo vincula snapshots `AVAILABLE`, y la vinculación usa `UPDLOCK` sobre la fila del snapshot. Retirar exige que ninguna generación retenida lo referencie y se hace con el mismo bloqueo, así que las dos operaciones se serializan.
- Estados de la generación: `… → RETIRING → DELETED`. Está prohibido retirar la generación vigente de cualquier canal, las incluidas en la ventana de rollback y las que tengan retención legal **[?]**.
- Orden de eliminación: (a) SQL marca `RETIRING`, (b) se borran los archivos, (c) SQL marca `DELETED`. Si falla a mitad, el recolector completa la operación de forma idempotente.

### 4.4 Integridad continua y restauración
- **Scrub** periódico (`nexus verify --all`): recalcula los hashes. Si no coinciden o falta el archivo, se marca `CORRUPT` o `MISSING`, la generación deja de ser publicable y se alerta. Si es la generación vigente, los lectores fallan cerrado y el operador hace rollback a la última generación certificada verificada.
- **Restore**: después de restaurar SQL o el FS, `nexus reconcile` compara filas y archivos. Las filas sin archivo pasan a `MISSING`. Los archivos sin fila van a cuarentena y no se borran automáticamente.
- **[?]** Tipo de almacenamiento (disco local, SMB, NAS), backups y WORM. Las semánticas de `fsync`/`rename` deben certificarse en el almacenamiento real (P5).

### 4.5 Certificación independiente y modelo de amenaza (revisión final)
- **El productor no puede autocertificar mediante metadatos.** Las filas que registra el productor son *afirmaciones*. La certificación usa únicamente valores recalculados por el certificador a partir de los bytes.
- **Separación en el FS**: `work/` (escribe el productor), `certified/` (escribe solo el certificador; el publicador y los lectores tienen solo lectura). Las ACL reales con cuentas de servicio distintas están pendientes (P13). En E1-C se simulan con identidades y directorios separados.
- **Modificaciones entre verificación y publicación**:
  - El productor no puede tocar `certified/`.
  - El publicador reverifica justo antes del CAS (paso 7).
  - **Control final**: todo lector verifica el `content_hash` certificado al leer y falla cerrado si no coincide.
  - Por tanto, una modificación en cualquier momento, también después de publicar, se **detecta antes de consumir el dato**.
- **Administrador privilegiado** (`sysadmin`, DBA o administrador del FS):
  - Una cadena de hashes en la misma base **no** es evidencia suficiente, porque quien controla la base puede recalcularla.
  - Propuesta **[D, sujeta a infraestructura]**: el certificador **firma** cada certificación (por ejemplo con Ed25519) sobre `manifest_hash`, los hashes certificados, `policy_hash` y la secuencia de publicación. La clave privada está bajo custodia fuera del alcance del DBA y del administrador del FS (P16). Los lectores verifican la firma con la clave pública distribuida en el repositorio de código.
  - Para detectar borrados o *replays* de registros antiguos, los digests firmados se anclan periódicamente en un destino append-only externo a la base (WORM, SIEM u otro, a definir en P5/P14).
  - **Riesgo residual declarado**: mientras P5, P14 y P16 no se resuelvan, el sistema **no protege ni garantiza la detección** frente a un administrador privilegiado. Esto no se presenta como resuelto.

## 5. R4 — Niveles de reproducibilidad

| Nivel | Definición | Se garantiza cuando | Cómo se verifica |
|---|---|---|---|
| **L1 Equivalencia lógica** | Mismo multiconjunto de registros por clave. Valores exactos para enteros, decimales, cadenas y fechas. Coma flotante dentro de una tolerancia declarada por columna en el contrato o CRC. | Mismos snapshots, contratos, mappings, CRC, parámetros, `as_of` y semillas, aunque cambien la plataforma o las librerías. | Comparador lógico (`replay --level L1`) |
| **L2 Reproducibilidad numérica** | Igual que L1, pero con valores idénticos bit a bit. | Además, misma **huella de entorno** (lockfile, Python, SO/arquitectura, tzdata) y operaciones de orden determinista. | `logical_hash` idéntico |
| **L3 Identidad byte a byte** | Archivos idénticos. | Además, misma versión del escritor Parquet y parámetros de escritura fijos (compresión, tamaño de row group, metadatos). | `content_hash` idéntico |

- **[D] Se versiona y se guarda en el manifiesto**: hashes de snapshots, commit git, hash del lockfile, versión de Python, SO y arquitectura, versión de tzdata, versiones de contratos, mappings y CRC, versión de cada motor, parámetros con su hash, `as_of`, semillas, configuración de hilos y parámetros del escritor.
- **[D] Reglas para preservar L2**:
  - Cantidades y horas en **decimal o entero de punto fijo** cuando el CRC lo permita.
  - Agregaciones de coma flotante con orden determinista (ordenar antes de reducir, sin reducciones paralelas no deterministas).
  - Nada de reloj, red ni aleatoriedad sin semilla en los motores.
  - Normalización Unicode NFC en la normalización de datos.
- **`logical_hash`**: serialización canónica propia, definida en el contrato y estable entre versiones de librerías: filas ordenadas por clave, codificación tipada por columna y NFC.
- **Condiciones que impiden reproducir**:
  - Snapshot purgado por retención: no se puede reproducir.
  - Cambio de librería o tzdata: L3 se pierde y posiblemente L2.
  - Cambio de CPU o plataforma (FMA, SIMD): posible pérdida de L2.
  - CRC o contratos modificados sin una nueva versión: está prohibido y se detecta por hash.
  - Componentes externos no deterministas: se prohíben en los motores.
- **[D] Datos de negocio vs. metadatos de ejecución** (revisión final):
  - El **`input_manifest`** es la identidad de reproducibilidad: snapshots, código, contratos, parámetros, `as_of`, semillas y huella de entorno. Su hash es el `input_digest`.
  - El **`run_record`** contiene `run_id`, `gen_id`, *attempt*, marcas de auditoría, host, rutas e identidades. **Queda excluido** de toda comparación.
  - El **`result_digest`** es el hash de la lista ordenada de `(contract_id@versión, logical_hash)`. Solo cubre datos de negocio.
  - Los artefactos **no contienen** `run_id`, marcas de tiempo de ejecución ni rutas en sus columnas ni en los metadatos Parquet. `as_of` es una entrada, no una marca de auditoría.
  - Las rutas son relativas y se nombran por hash dentro del directorio de cada generación.
  - Por tanto, dos corridas con el mismo `input_digest` y distinto `run_id`, distintas marcas o distintas rutas deben dar el mismo `result_digest` (L2) y los mismos `content_hash` (L3, en el mismo entorno).
- **[D] Política**: L1 es obligatorio dentro de la ventana de retención. L2 y L3 son obligatorios con la misma huella de entorno. `replay` informa el nivel alcanzado y la primera discrepancia.

## 6. R5 — Separación de roles y autoridad

| Rol | Principal SQL | Puede | No puede |
|---|---|---|---|
| **Productor** (worker de pipeline, manual o programado) | `nexus_producer` | Reclamar solicitudes, lease, registrar snapshots y artefactos, sellar generaciones | Escribir hallazgos, certificar, publicar ni modificar políticas |
| **Validador** | `nexus_validator` | Leer generaciones `SEALED` y artefactos, insertar `finding` | Modificar generaciones, certificar ni publicar |
| **Certificador** (automático o humano según la política) | `nexus_certifier` o usuario humano nominal | `usp_certify` | Certificar generaciones producidas por su propio principal ni publicar |
| **Publicador** | `nexus_publisher` | `usp_verify_for_publish`, `usp_publish`, `usp_rollback` | Certificar ni producir |
| **Autoridad de autorización** (humanos designados [?]) | `nexus_policy_admin` (uso controlado, fuera del runtime) | Registrar y activar versiones de política y aprobar CRC | Activar una política de la que es autor (dos personas) |
| Lector (web y reportes) | `nexus_reader` | `SELECT` sobre vistas de la generación publicada | Cualquier escritura salvo `run_request` (rol aparte `nexus_requester`) |

**Controles aplicados en la DB** (dentro de los procedimientos y con `DENY` de escritura directa en tablas):

- `usp_certify` verifica:
  - La generación está `SEALED` y su `manifest_hash` coincide.
  - Todos los artefactos se reverificaron después del sellado.
  - Existe una política `ACTIVE` cuyo `policy_hash` coincide con la que evaluó el certificador.
  - Hay hallazgos registrados por `nexus_validator` para esa generación.
  - Ningún `BLOCKER` queda sin una excepción aprobada por la autoridad.
  - Ningún dominio está en `RULES_PENDING`.
  - El principal que llama es distinto del productor.
  - Si la política exige aprobación humana, el aprobador es distinto del solicitante del run.
- `usp_publish` verifica:
  - La certificación es válida y no está revocada.
  - La política sigue activa.
  - El canal está autorizado por la política.
  - Hay una verificación previa a publicar de menos de *T* minutos.
  - El CAS se cumple.
  - Inserta en el historial con `prev_hash`. Esto es solo una ayuda de integridad interna, **no** evidencia frente a un administrador privilegiado (ver §4.5).
- Las ejecuciones manuales y programadas usan los mismos roles. El disparo solo crea un `run_request`. Una cadena programada puede ejecutar `produce → validate → certify → publish`, pero **cada paso usa su credencial**, y las credenciales de certificación y publicación no se exponen al proceso productor.
- **[?]** Uso de cuentas de servicio AD o logins SQL, gestor de secretos y auditoría del servidor (SQL Server Audit). Es infraestructura y queda pendiente.

### 10.1 Precisión 1: compatibilidad Windows/NTFS
- Toda operación dependiente de la plataforma queda aislada en `src/nexus/storage/_fs.py`. La lógica del ObjectStore no contiene rutas ni llamadas específicas de un SO.
- Las rutas internas son claves relativas POSIX validadas:
  - Solo `[a-z0-9._-]` y `/`.
  - Sin `..`, sin rutas absolutas ni letras de unidad, sin nombres reservados de Windows (`CON`, `NUL`, `COM1`…), sin `:` (ADS), sin espacios o puntos finales.
  - Longitud acotada para no superar `MAX_PATH`.
  - Se convierten a la ruta del SO solo en `_fs.py`.
- Escritura binaria exclusiva; nunca modo texto. La E/S de manifiestos es JSON canónico UTF-8 con `\n` explícito.
- Tabla de garantías que se entregará en `docs/evidence/E1-A/PLATFORM_GUARANTEES.md`:

| Garantía | Linux (ext4/overlay del sandbox) | Windows/NTFS |
|---|---|---|
| Publicación sin reemplazo | **Demostrada por pruebas** (`os.link`, que falla si el destino existe) | Diseñada (`os.link` → CreateHardLink, o `os.rename` → MoveFileExW sin REPLACE_EXISTING). **Pendiente de certificar.** |
| `fsync` del archivo | Demostrada a nivel de API; la durabilidad ante corte eléctrico **no** se demuestra | `os.fsync` → FlushFileBuffers. Pendiente. |
| `fsync` del directorio | Se ejecuta | **No disponible en Windows.** La durabilidad del rename en NTFS queda pendiente de certificar (posible `MOVEFILE_WRITE_THROUGH` en el futuro). |
| Marcado de solo lectura | `chmod 0o444` (disuade, no impide a root) | Atributo read-only (disuade). Las ACL reales están pendientes (P13). |
| Recursos SMB/NAS | No probado | No probado (P5) |

- En CI se añade un job `windows-latest` que ejecuta la misma suite como **evidencia informativa, no como certificación**. Si no puedo observar su resultado, se reporta como "no observado".

### 10.2 Precisión 2: sin sobrescrituras ni sustituciones concurrentes
- **Nunca** se usa `os.replace` ni `shutil.move` en `src/`. Un test de arquitectura (AST/grep) falla si aparecen.
- Protocolo de publicación de un objeto:
  1. Se escribe en `staging/<uuid>.tmp` con `O_CREAT|O_EXCL` y se calcula el hash en streaming.
  2. Se hace `fsync`.
  3. **Enlace sin reemplazo** al destino. Si el destino existe, se lanza `FileExistsError`.
  4. Se hace `fsync` del directorio cuando la plataforma lo permite.
  5. Se relee y verifica el destino.
  6. Se elimina el temporal.
  7. Se marca el destino como solo lectura.
- Si el destino ya existe, se verifica su hash:
  - Si coincide, la operación es idempotente y no escribe nada.
  - Si no coincide, se lanza `ImmutableConflictError` y el archivo existente nunca se toca.
- Si el FS no admite hard links, se usa como respaldo `os.rename`, pero **solo** en plataformas con semántica de no-reemplazo (Windows). En POSIX, ante esa situación, se lanza `UnsupportedFilesystemError`: falla cerrado, sin degradar a un rename que reemplace.
- **Pruebas adversariales adicionales**, dentro de los criterios A4 y A5, sin ampliar alcance:
  - 8 procesos escriben concurrentemente el mismo objeto con el mismo contenido: un solo archivo final y verificado, y todos los procesos terminan con éxito.
  - 8 procesos escriben concurrentemente contenidos distintos bajo la misma clave: exactamente uno gana y los demás reciben `ImmutableConflictError`. El contenido final coincide con el del ganador.
  - Archivo plantado en el destino antes de escribir: se detecta y se lanza un conflicto, nunca se sobrescribe.
  - Sustitución tras la escritura (se cambia el archivo final por otro): `IntegrityError` al leer.
  - Destino convertido en enlace simbólico: se rechaza (`lstat` y no se siguen enlaces).
  - Test estático que garantiza la ausencia de `os.replace` y `shutil.move`.
